Project Overview

What it is

ServeEM is a fast-paced arcade mobile game where players prepare and serve burger orders while dealing with unpredictable disruptions that challenge memory, reaction speed, and adaptability.

Why it was built

This project was built to explore what makes a gameplay loop engaging and replayable, balancing unpredictability, player mastery, and score-chasing. To keep the focus sharp, it was scoped as a 1-month solo project taking the game from concept to release, intentionally small enough to experience the full mobile development pipeline end to end.

What it covered

The project provided hands-on experience shipping a mobile game to the Google Play Store, including Google Play Games Services integration, Play Store submission, platform compliance, and gameplay balancing for long-term player retention.

What I Did

Design and Prototyping

Started with rough flow diagrams in draw.io to map out the order loop, malfunction triggers, and state transitions before writing any code. UI layout was sketched out early to nail button placement and on-screen feedback. These were then carried into an early Unity 2D prototype to validate the core interactions before any final art was in place.

Playtesting and Iteration

Ran playtesting sessions with peers to evaluate pacing and difficulty. The main focus was tuning which random effects appeared and when, defining the unlock thresholds and set progression so that disruptions felt challenging without being arbitrary. Feedback from each session directly informed adjustments to the effect pool, spawn timing, and difficulty curve before the next round of testing.

Leaderboard Integration

Integrated Google Play Games Services to add a live leaderboard, giving players a competitive hook beyond personal score. This was also a deliberate opportunity to gain hands-on experience working with an external API inside a shipped game, covering authentication flow, score submission, and surfacing the leaderboard in-game.

Publish and Monitor

Submitted the game to the Google Play Store, working through the full compliance checklist including content ratings, data safety declarations, privacy policy, signing key management, and staged rollout. After launch, monitored user reviews and store feedback to identify issues and track reception.

Monetisation and Analytics

Integrated Unity Ads for ad-based monetisation and Unity Analytics to track DAU, MAU, and average score. This was primarily an exercise in gaining practical experience with monetisation tooling and using real usage data to identify balance issues and inform tuning decisions.

What I Learned

Working alone meant full creative control, but also no one to catch what I'd stopped noticing. Playtesters flagged unclear icons and pacing issues I couldn't see myself. Outside feedback changed the game in ways internal review never could.

Layouts that felt fine on my device broke on others, with tap targets becoming cramped or misaligned. In a game built on speed and precision, a misaligned button is a gameplay bug. Responsive layout needs to be a first-class concern from the start.

The code was done before the release was. Content ratings, data safety forms, privacy policies, signing keys, and staged rollouts all added work I hadn't planned for. I now understand why studios have dedicated production roles.

Adding ads is easy. Making them work without hurting retention is not. Placement depends on timing relative to player state, not gut feel. Monetisation deserves the same rigour as core gameplay.
